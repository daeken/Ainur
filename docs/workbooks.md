# Arda workbooks (first increment)

The project **Workbooks** tab and native `workbook` agent tool share the same SQLite records. A local authenticated API client may also use `/api/v1/projects/{projectId}/workbooks` (existing local-origin/X-Ainur control-plane policy). `POST` creates `{ "title": "..." }`; `GET` lists; `GET /{bookId}` returns the workbook, ordered cells, runs and per-cell `stale`. `POST /{bookId}/cells` takes `{ "language": "powershell", "source": "Write-Output 21" }`. `PUT /{bookId}/cells/{cellId}` takes `{ "expected_revision": 1, "source": "Write-Output 42" }` and returns HTTP 409 on concurrent edits. `POST /{bookId}/cells/{cellId}/runs` takes `{ "revision": 2 }`; `GET /.../runs` reads saved outcomes. Exact saved old revisions can be run intentionally through the API or native tool; a nonexistent revision returns HTTP 409. No GET runs anything.

Agent tool actions: `list`, `create` (`title`), `open` (`workbook_id`), `add` (`workbook_id`, `source`), `edit` (`workbook_id`, `cell_id`, `expected_revision`, `source`), `run` (`workbook_id`, `cell_id`, `revision`), `runs` (`workbook_id`, `cell_id`). The agent's current project is implicit: workbook IDs outside it do not open/run. The same saved revision/source, chronological per-cell run ordinal, actor, start/end, status, stdout and stderr are durable. Durable intent is `unknown` until completion commits. While this server owns a live invocation, reads surface `queued` or `running` using process-local ownership shared across API/tool instances; a second run of the same active cell is rejected. Restart loses that ownership, so orphan intent remains `unknown`, never automatically retried. Investigate external effects before manually rerunning. Each run has a fresh PowerShell runspace **inside the server process**, with project workspace as starting directory; not a fresh OS process, and no cross-cell variables or cross-language session. A canceled token detected before execution admission records `canceled` (cell code not started). Cancellation after admission or the two-minute deadline requests cooperative PowerShell Stop and surviving interrupted invocations record `interrupted`; this is **not a hard timeout or native-child-process termination guarantee**. `unknown` or `interrupted` cannot prove an external side effect did not happen. No auto-retry or execute-on-reload.

This first slice has only PowerShell, no C# cell runner, no durable interactive shared kernel or automatic dependency scheduling. PowerShell runs with the same local server OS privileges as the existing PowerShell tool: the workspace is a starting directory, **not a filesystem/process/network sandbox**. Treat editing/running workbooks as trusted local control-plane operations. Source is limited to 64,000 characters; saved output/error text is truncated to 64,000 characters **after buffered invocation completes, not a peak-memory bound**, and there is no execution-cost accounting for local scripts. For errors, output includes PowerShell pipeline and host/information records, and stderr includes PowerShell error records and nonzero native exit. The UI only offers the current saved revision for running; API/tool can run historical revisions explicitly.

Offline proof: `dotnet test tests/Ainur.Tests --filter 'Category!=Live'`; `npm --prefix web ci && npm --prefix web run build`. Tests cover per-project scope, CAS conflict, stale output, persisted reload, historical revision, output/error, fresh runspace, pre-admission cancellation without side effects, active status across readers, duplicate-active rejection, interrupted-vs-orphan unknown provenance without retry. Server/API demo requires an isolated `--home` and workspace; never point a workbook at a production instance to verify it.

## Concurrent initialization repair

Both session hosts and workbook runs use one shared runspace-open fence for default-drive initialization. Execution remains concurrent: a paired-cell rendezvous test proves neither pipeline waits for the other's entire invocation. macOS cold concurrent initialization on the unfenced workbook path reproduced a testhost native access violation in `Interop.Sys.AddMountPoint/GetAllMountPoints` → `DriveInfo.GetDrives` → `FileSystemProvider.InitializeDefaultDrives`. The existing session-only gate did not protect workbook opens; .NET's macOS `getmntinfo` enumeration uses a shared native buffer. `WorkbookInitializationTests.ConcurrentWorkbookAndSessionInitializationPreservesEachWorkspace` mixes real session-host opens and workbook writes into distinct isolated workspaces; it must pass without serializing tests or all executions. This addresses the observed initialization race, not a general promise of PowerShell/native thread safety.
