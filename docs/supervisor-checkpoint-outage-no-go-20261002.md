# NO-GO: externally sealed checkpointed outage on loaded e022 runtime (2026-10-02)

**Decision:** Source-only future-supervisor fixes cannot make a controlled service outage safe while the *loaded* e022 server lacks an exclusive, durable admission seal. Do **not** invoke `/control/drain`, `/control/stop`, SIGSTOP, SIGTERM, `launchctl bootout/bootstrap`, release activation, or the archived v2 reload on this report. No live controls, process mutations, credential/model probes, or database changes were made.

## Exact authority boundary

Root conditionally permits ONE full-service maintenance outage with controlled termination of **only** the exact dedicated old supervisor/runtime processes **AFTER** independent evidence proves no *current* active/outcome-unknown work. The old historical reconciled `unknown` provider/tool rows must remain UNKNOWN and are not a justification to invent an outcome. Eönwë must own go/no-go and detached recovery; Námo independent gate precedes action. A manager-hosted tool invocation is itself active work; a detached coordinator must observe only **after** that manager turn completes and must not rely on the process it would terminate.

## Source-bound admission and dispatch counterexample

Historical exact deployed source `/private/tmp/ainur-final-e022` (commit `e0224064439ef30c71810ddc9ebdc9b38086be8f`; source inspection only):

- `src/Ainur.Server/Program.cs:17,31,34,40,46`: Kestrel listens directly on `http://127.0.0.1:5181`; local middleware and API map run alongside `runtime.Start`. No distinct launcher-controlled proxy/listener owns the only ingress. `src/Ainur.Server/Hosting.cs:53-75`: localhost Host and `X-Ainur: 1` are caller-supplied checks, not an exclusive maintenance lock; existing accepted connections are not revoked by subsequently filtering *new* connections.
- `src/Ainur.Server/Api.cs:126,140-146,216-225`: `/agents/{id}/resume`, POST `/projects/{id}/conversation`, `/control/drain`, `/control/undrain`, and `/control/stop` are reachable while the listener runs. The owner can send drain, but a later permitted POST undrain explicitly reopens dispatch; an HTTP status alone is not a durable admission guarantee.
- `src/Ainur.Core/Runtime/AinurRuntime.cs:177-190`: drain writes only volatile `Draining=true` then polls `Hosts.Values.All(h => !h.IsRunning)` at 100ms intervals; undrain sets `Draining=false` and wakes all. It neither persists a maintenance owner nor locks all future calls nor waits for a specific ordered worker/callback checkpoint. `AinurRuntime.cs:220-224` checks `Draining` for its *normal* `Wake`, but `Coordination.cs:78,101-102`, `Organization.cs:329,404` and retry `AinurRuntime.cs:312` call `SessionHost.Wake` directly; they queue wake requests even during draining. `SessionHost.cs:51-54,58-94,126-131` sees the volatile flag at each work boundary and does not cancel a current provider/tool call. Queued wake/work can resume immediately after any undrain or fresh child startup.
- `AinurRuntime.cs:79-99,102-153` starts a new generation and recovers historical inflight work on process restart; previously dispatched provider rows become `unknown`, not confirmed no-side-effect. The supervisor fixes do not modify the old loaded child's admission state.

**Adversarial schedule (finite, no action performed):** T0 independent observer samples zero currently running hosts and no current inflight row after an in-process drain. T1 an already accepted loopback HTTP POST `/control/undrain` is processed, or a delayed internal wake is queued; there is no external transaction that can prevent both transitions. T2 a pending user notification/session step begins provider dispatch. T3 observer begins SQLite backup or exact-process termination based on the stale T0 sample. T4 current model/tool outcome becomes unknown or duplicated across recovery. Reversing T0/T1 does not fix it; a second sample can race a third accepted request. Network PF/listener shutdown would not revoke accepted connections, direct in-process timers/wakes, or an in-flight request; the direct Kestrel socket has no supported detached accepted-connection drain/owner seal. `/control/drain` only stops at a step boundary and is explicitly reopened by `/control/undrain`.

## Required independently provable gate, not currently available

A safe future procedure would need one exclusive admission-and-dispatch owner that can persistently reject **all** inbound mutation, `/undrain`, resume/new work, old accepted connections, and internal fresh work after its closure, while allowing current calls to reach committed boundaries. **Then**, after Eönwë's last agent tool turn returns, a detached actor would check the seven-agent manager tree and preserved Tulkas pause; every existing host, pending delayed retry, current model/tool request, notification/work queue and ledger reservation; read-only WAL-consistent SQLite backup including db/-wal/-shm or SQLite Online Backup API; exact parent/child PID+start+port+release/gen and immutable launchd label/plist hashes; recovery actor independent of the dying processes. Historic UNKNOWN remains separately recorded. Any nonzero current work or inconclusive observation => NO-GO, no retry/kill.

No existing external, reversible **simple** gate is source-proven to enforce this invariant in the loaded e022 process. Implementing a new persistent runtime admission state checked at every dispatch/mutation path plus a gated detached controller, or separately authorizing a proven system-level exclusive process/socket scheduler, is **new work/authority** and requires independent design and offline adversarial tests before a new go/no-go. A firewall/loopback redirect, polling hosts, retrying drain, or claiming the future supervisor one-use spawn lease applies to the old child is not a substitute.

Future source `ainur/ulmo/supervisor-checkpoint-safe` commit `aa2b30bba7379909e3c61a2c965bf7a998bfa619` is **source-only**: subscription pin on every new child spawn, no forced kill, one-use fsynced claim blocking KeepAlive relaunch, unexpected child exit/malformed inflight fail closed. It is not deployed and is not a maintenance checkpoint proof. Its one-use claim intentionally blocks restart until a separately authorized detached operator independently proves old process absence and ledger/route/pause state and clears it; never auto-clear or blindly retry.
